# WeFlow Personal OS 产品路线图

> 目标：把本机微信增量数据变成一个证据可追溯、可搜索、可对话、可持续成长的个人行动与记忆系统。
>
> 原则：本地优先；微信 ID 是身份锚点；原文证据不可丢；不确定内容不冒充事实；所有自动合并可撤销；断电、离线和重启后可续跑；API Key 永不写入仓库。
>
> 产品硬规则：任何新增的后端记忆能力，必须在同一阶段提供可查看、可理解、可确认、可拒绝或可纠正的前端入口，不能只落库。

## 当前基线

- [x] 微信数据本地读取、时间戳增量续跑、启动补齐和每日调度
- [x] DeepSeek结构化抽取与 JSON 校验
- [x] 按会话分片，100 条核心消息与前后各 20 条重叠上下文
- [x] 联系人备注、微信昵称、群昵称、微信号与 wxid 身份 mapper
- [x] 信息来源开关及公众号硬过滤
- [x] 待办归属 `mine / uncertain / others` 与人工确认
- [x] 人物、组织、群、项目实体及有向关系
- [x] 关系原文证据、方向说明和人工确认
- [x] 增量身份消歧、正反决策持久化、可撤销合并
- [x] SQLite、全文搜索表和向量字段基础结构

## P0：可信个人记忆核心

### P0.1 个人事实 Claims

- [x] Prompt 同时抽取主语、谓词、值、有效期、置信度、来源性质
- [x] 区分本人陈述、他人陈述、模型推断和人工确认
- [x] 同一事实追加证据，不覆盖历史
- [x] 互相冲突的事实并存并进入确认状态
- [x] 支持事实人工纠正、有效期和纠正审计记录；人工纠正使用事务同步结构化值、状态、全文与向量失效，后续同 ID 重抽取只能追加原文证据，不得覆盖人工值、确认状态、来源性质或搜索文本
- 验收：可以回答“我在哪些公司工作过”，并列出时间、证据和冲突。

### P0.2 事件与时间线

- [x] 抽取会议、承诺、交付、旅行、付款、加入/离开组织等事件
- [x] 保存参与者、角色、时间范围、地点和证据
- [x] 相同证据且时间相同/缺失的事件自动聚合
- [x] 界面展示基础个人时间线；事件可在时间线或问答引用中纠正标题、类型、说明、上海时区起止时间与地点，前后版本写入审计并标记最近纠正时间，后续重抽取只追加证据；确定性来源删除仍可将人工纠正事件标为已取消，但不改写其人工内容
- 验收：可以回答“上个月发生了哪些重要事情”，每项可回到原消息。

### P0.3 证据与可信度

- [x] 事实、事件和关系保存 messageId 证据
- [x] 根据陈述来源区分直接证据和间接证据
- [x] 抽取肯定式标准谓词 + 正负极性；冲突事实双向挂接明确反证并在界面标注
- [x] 没有证据的事实与事件拒绝落库
- [x] 所有模型结构统一执行落库前证据门禁：待办、实体、关系、事实、事件和身份合并建议均引用 `sourceId:sessionId:messageId` 复合 evidenceKey；只接受当前分析窗口的 core 消息，裸消息 ID、伪造键、跨会话同号消息和 overlap context 引用均在任何图谱/数据库变更前剔除；新证据记录使用复合键避免跨会话主键碰撞
- [x] 通用搜索证据同样采用会话级复合身份：资源、待办等 `search_document_evidence` 主键由“文档＋消息”升级为“文档＋会话＋消息”，不同群聊相同 messageId 可同时持久化、分页展示并准确跳回原文；启动核验真实主键列顺序，旧库事务化重建并保留现有证据，迁移次数、去重数和约束健康进入数据库门禁及前端诊断
- [x] 通用搜索证据具备数据库级引用完整性：`document_id` 以 SQLCipher `ON DELETE CASCADE` 外键锚定搜索文档，并保留受启动校验的删除触发器作为派生载荷双保险；启动同时核验会话消息定位索引，旧库迁移前剔除历史孤儿证据，外键、索引、累计迁移和孤儿清理量进入健康门禁及前端诊断
- [x] 通用搜索证据保留完整跨来源身份：资源和待办原文由“文档＋来源＋会话＋消息”四段复合键去重，微信、文档、日历和邮件即使出现相同会话与消息 ID 也能同时留存；旧库从既有复合消息键或 `data-source:` 会话确定性回填来源，无法证明的历史行明确标为 `legacy`，检索卡片、RAG 引用、任务/人物/项目档案和完整证据分页统一展示真实来源
- [x] LLM 新增事实、事件和关系一律进入候选；只有人工操作与确定性规则可以确认
- [x] 实体摘要采用非破坏性证据候选：模型摘要必须绑定当前 core 原文，默认不写入可信实体摘要、不进入全文/向量检索、也不回送模型；界面同时展示建议摘要、现有摘要和逐条原文，人工确认后才生效，确认时若现有摘要已变化则候选自动失效，旧版无状态摘要明确标记“历史未验证”并从可信检索隔离
- [x] 增量抽取使用有界可信长期上下文：不再把任意最近 200 个实体整体发送给模型，而是从当前消息发送者 wxid、本人身份、正文/会话中的规范名与已确认别名确定性命中最多 24 个可信实体，再仅扩展一跳已确认关系；只回送已确认摘要、事实和事件，候选及二跳内容严格隔离，同名不同 ID 保持并存；Prompt 明确长期记忆只能消歧而不能充当本批新结论证据，所有新增结构仍须通过当前 core 原文门禁，每批命中数量和上下文版本随崩溃一致提交日志持久化并在完整诊断中展示
- [x] 可信上下文具备可审计清单：每批对实际脱敏后模型输入连同系统 Prompt 计算不可逆 SHA-256 指纹，记录 core/overlap 数量、所选实体及逐项命中原因、已确认关系、事实和事件的有界结构化清单；实体 24、关系 40、事实 36、事件 16 及各字段长度均有独立硬限制，清单不复制聊天正文，跟随 prepared 重放协议写入 SQLCipher；完整诊断可展开核验 DeepSeek 当时获得了哪些长期记忆，同时兼容旧版仅计数记录
- [x] 建立首批 SQLite 回归测试，覆盖冲突事实、任务证据和中文检索回退
- [x] 建立任务归属匿名化合成黄金集和版本化规则评估器；后续持续追加真实错误的匿名变体
- [x] 结构化记忆卡片与图查询统一原文追溯：事实、事件、最短路径和共同实体均展示证据并可从合法微信复合键打开原消息；文档、日历等数字结尾外部 ID 不会误触发微信跳转。事实/事件每项只附最近 20 条、关系边只附最近 8 条，同时返回真实证据总数并引导到统一检索查看完整历史；同时间的主证据稳定排在反证之前，长期积累不会使首页或图查询载荷随证据数无限增长
- [x] 深度审阅视图复用统一证据契约：人物完整档案的事实、事件、关系和任务，跨源事件时间线，以及项目档案的任务、里程碑、决策和聚合证据全部使用同一来源/时间/角色规范与合法微信原消息入口；任务、事实和事件每项最多返回最近 20 条，关系边最多 8 条，项目聚合最多 50 条，同时保留各自真实总数。dashboard 不再随每条任务重复传输全部历史证据，项目派生视图也不会把同一大段证据再次无限复制
- [x] 结构化证据发送者与真实去重：事实、事件和关系的权威 evidence 表持久化发送者，重复抽取同一结构＋同一消息时只补全发送者而不新增副本；修复旧版包含可空外键的 UNIQUE 约束无法阻止 SQLite NULL 重复的问题，启动一次性合并既有重复行，保留非空发送者、最长摘录和 contradiction/direct 优先角色，并从通用证据索引尽量回填旧发送者；随后以 claim/relation/event 三个部分唯一索引持续保证身份约束。卡片、人物/项目档案、完整证据历史和 RAG 引用统一显示发送者，未知旧数据明确标注而不猜测；迁移前后行数、移除重复数、发送者恢复数和时间写入加密 schema 审计并在首页与完整诊断可见
- [x] 结构化证据唯一约束持续自愈：启动不再只相信一次性迁移版本，而是核验三项索引的唯一性、部分索引条件、列顺序和 SQL 条件；索引缺失或定义漂移时先合并漂移期间产生的重复证据，再原子重建全部约束。累计自愈次数、约束健康状态和本次是否发现漂移写入 SQLCipher 审计并在健康页可见
- [x] 结构化证据保留完整跨来源身份：事实、关系和事件的权威 evidence 表显式保存来源，并按“结构 ID＋来源＋会话＋消息”建立部分唯一索引；微信、文档、日历与邮件即使使用相同会话和消息 ID 也不会互相覆盖。旧库只从 `data-source:` 会话或已知复合消息键确定性回填，无法证明的历史行保留为 `legacy`；来源回填量、身份版本与约束健康进入数据库门禁和前端诊断，所有结构化证据卡片继续显示真实来源。
- [x] 结构化证据引用完整性自愈：补齐旧 schema 中关系和事件删除不会外键级联证据的缺口，以受校验的 SQLCipher 删除触发器保护新数据；每次启动分别扫描事实、关系和事件孤儿证据并原子清理，累计清理量、触发器修复次数、原生 foreign key check 与当前健康状态进入诊断，备份前也必须同时通过文件、唯一约束和引用完整性检查
- [x] 结构化记忆与检索索引双向对账：每次启动删除本体已经不存在的事实/关系/事件幽灵搜索文档及其 FTS、通用证据和 ANN 派生载荷，同时从权威结构表重建“仍存在但搜不到”的缺失文档并使向量重新进入增量补齐；数据库触发器保证今后删除本体会级联清理搜索文档，删除搜索文档会清理二级载荷。结构化原文不复制进缺少证据角色的通用表，继续直接读取权威 evidence，保留 direct/indirect/contradiction 语义；累计删除、重建、触发器修复和当前一致性进入健康门禁与界面诊断
- [x] 搜索文档与 FTS 载荷逐项一致性：启动对全部统一检索文档核验恰好一条且标题、正文完全一致的 FTS5 行，缺失、重复或过期载荷统一删除后从权威 search_documents 重建；既有文档无需重新调用模型或重建结构化记忆即可恢复关键词召回，累计 FTS 修复量及当前载荷漂移状态进入同一健康诊断
- [x] 结构化搜索可信元数据对账：以 claims、relations、events 权威表核验搜索文档中的状态、正负极性、主客体、关系谓词、有效期、事件类型/时间和参与者；JSON 损坏或字段过期时只修复 metadata，不重写正文、不调用模型、不无谓失效仍有效的向量。已拒绝内容重新退出普通检索与 RAG，人物/关系/时间范围恢复正确召回；累计修复量与当前漂移进入检索健康门禁和界面诊断
- [x] 结构化搜索权威正文与身份对账：事实、关系和事件的搜索标题、正文、内容哈希、文档类型、来源 ID 必须与本体同时一致，不能因 FTS 与错误搜索文档“共同漂移”而误报健康；正文或哈希漂移时从本体恢复并精确失效旧向量，类型/来源错配时按幽灵清理后以规范 ID 重建，累计正文修复量进入健康诊断
- [x] 事实与事件支持“不重要”轻量清理：一次普通确认后事务删除结构化正文、原文证据、参与者/纠正记录、全文/向量索引和引用它的本地问答，使数据库页可供后续记忆复用；仅保留不含正文的类型、不可逆指纹、影响计数和 `not_important` 原因，语义抑制指纹保证同一原文即使换模型措辞重跑也不会复活。界面与永久删除分开呈现，并在统一审计中明确区分“不重要清理”
- [x] 事实与事件的人工可信决定不可被重抽取覆盖：确认、不准确及从拒绝恢复确认均追加写入 SQLCipher 审阅账本；只要存在人工决定，同一确定性 ID 的后续模型结果只能追加去重原文，不得改写结构化内容、可信状态或检索元数据。启动时旧版自动确认降级也绕过人工决定；档案卡展示累计决定次数、最近时间及最近 20 次“原状态→决定”的可展开历史，事件时间线补齐“不准确”筛选和恢复确认入口，永久删除和实体级联删除同步清理审阅记录。
- [x] 可信决定区分人工裁决与系统级联：审阅账本显式保存执行者、可读原因及是否阻止重抽取；实体暂未确认造成的系统降级只留下可见审计、不冒充人工操作也不冻结模型后续更新，用户拒绝实体触发的事实/事件级联拒绝则继续受到保护。旧版账本无损补列，前端审阅历史明确显示“本人操作/系统规则”和触发原因。
- 验收：任何界面结论都能展开查看原文、发送者和时间。

### P0.4 增量运行可靠性

- [x] ingestion run 持久化记录每批消息量、模型、Prompt 版本和结果
- [x] 每批持久化结构化证据门禁版本及六类输出的接受/拒绝数量，完整诊断页展示无效引用被拦截的数量
- [x] 分批写入与 checkpoint，单批失败不丢失前批结果
- [x] JSON 自动修复与失败批次重试
- [x] 失败批次本地保留并在下次按 checkpoint 重试；支持当前批次后安全暂停、继续和实时批次进度/错误界面
- [x] 微信与文档模型结果使用可重放提交协议：结构化 digest、原批次、精确消息键、来源类型及文档内容版本先写入 SQLCipher prepared 日志，图谱、事实、事件、待办与加密状态全部耐久保存后，再用同一 SQLite 事务提交日志、批次状态和文档分析 checkpoint；任一写入窗口断电后启动会直接重放本地结果而不重复调用模型，实体 ID 按批次确定化避免重复建人，文档已变化时旧批次不能越权推进新版内容，界面按微信/文档显示待恢复数量与失败保留状态
- [x] 启动时对账遗留 ingestion run：在 prepared 重放之后扫描仍为 running 的旧运行，于 SQLCipher 单事务内保留已完成批次和消息量、将真正的在途批次转为等待 checkpoint 重试、记录尚待恢复的加密载荷，并把整次运行归档为带恢复时间和计数的 partial；重复启动幂等，首页和完整诊断明确区分当前运行与上次退出中断
- [x] 成功消息使用 SQLCipher 无损去重账本：每个微信 core evidenceKey 与批次结果在同一提交事务写入，prepared 恢复复用同一路径，启动把旧版最近 20,000 条 JSON 热缓存幂等迁入账本；部分失败即使长期阻止时间游标前移、成功量超过热缓存上限，也会在模型调用前按最多 400 键分块查询持久账本，避免重复消耗 Token、重复任务和图谱污染，界面显示实际持久账本规模
- [x] 微信读取使用会话级失败水位：每个本轮需要读取的会话在首次 HTTP 请求前就把独立起点写入加密状态，不能依赖稍后才推进的全局时间戳；模型批次失败时任何相关会话和全局窗口都不前进，只有来源读取成功且全部模型批次成功的会话才推进；若部分会话读取失败，成功会话与全局窗口可安全提交，失败会话仍固定在失败前原始起点，整次运行和微信数据源标记 partial/error 并在首页显示待补齐会话数，重启或长期失败不会把旧消息滑出 5 分钟重叠窗口
- [x] 每日调度采用显式完成提交：只有微信分页与模型批次全部结束、没有安全暂停，并且所有已启用的文档/日历/Mail 连接器均成功时才写入 `lastScheduledRunDate`；高流量 continuation 或任一辅助来源失败只保存成功部分和 checkpoint，不再误标“今日已跑完”。调度持久化最近尝试、最近完整成功、失败原因和连续重试次数，同日最短 15 分钟继续尝试；首页明确显示未确认完成原因与下次重试时间，手动补齐也不会把 partial 结果显示成成功。
- [x] 每日调度重试跨重启收敛：下一次允许尝试的绝对时间写入加密状态，连续失败按 15/30/60/120/240/360 分钟指数退避并封顶 6 小时，应用重启不会绕过门禁立即重打失败连接器；存在定时失败时，后续手动、启动或积压补齐只有在所有来源完整成功后才提交当天完成并清除警示，partial 或异常继续推进退避。
